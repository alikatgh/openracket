Mac light tools and real Quit paths

2026-10-11

Run 38154975508, at source commit 96fe2b7, passed all 204 result rows on native Apple Silicon with full official Racket 9.3: 90 light/tools rows and 114 Quit rows. They cover 12 native cases plus preparation, controls and preservation checks, not 204 distinct workflows. The preview core and native app builder were unchanged. Reviewed acceptance report.

Six fresh stock/modern-light cases exercised the real tools. Debugger Step changed the fixture's program counter from 60 to 36 before Resume and ordinary Run recovery. Macro Stepper navigation checked indices 0, 1 and 82, Previous/Start, a changed derivation, normal close and Run recovery. Teaching tests followed the real failure link to positions 77–102, then an unsaved correction and rerun produced two passes and replaced the failure report. Modern light appearance was checked before and after each tool, including actual Cocoa Aqua, Framework colors and all 11 toolbar painter colors.

Six fresh stock/modern-dark cases covered clean Quit, Cancel then Save, and Cancel then Don't Save. The driver called the installed application Quit handler on its GUI eventspace and invoked the actual dialog button callbacks. Actual focus and edit-target witnesses preceded every Quit request. Cancel preserved the modified editor/tab and Unicode edit; the subsequent Save wrote exactly the intended UTF-8 bytes, while Don't Save retained the original disk bytes. All six cases exited naturally with code 0 and no cleanup used to manufacture success.

The complete 26,838-entry runtime comparisons for both groups passed, along with the combined run's original-preferences witness. The direct-launch runner began with no preferred .rkt handler and retained null → null throughout. This preserves an absent default in this scenario; the earlier app run separately preserved an existing Script Editor default through Launch Services. Neither result extends the other run's launch route.

Quit did not exercise Finder/Apple-event delivery, physical Command-Q input or a mouse click on the menu item. The confirmation preference was enabled; multiple dirty windows, other document formats, save failures, shutdown races and arbitrary extensions remain outside these fixtures. The previous clean-Quit timeout lacked actual activation evidence, so its historical cause remains unresolved. Light tool cases retained stock 128 MiB settings; Quit observed 128 MiB stock and 256 MiB modern preferences, without a new evaluator-cap measurement.

This adds functional evidence, with no speed claim or self-contained binary. The app remains tethered to full official Racket and separate source/profile paths, unsigned and not notarized. Download-time Gatekeeper behavior, full compatibility and further native Windows/Linux acceptance remain pending. The earlier autosave and capacity measurements retain their own scope.

Enough memory to complete the tested analysis

2026-10-11

A nine-trial stock DrRacket experiment tested the same 1 MiB file with 128, 256 and 512 MiB per-job memory limits. The 128 MiB setting ended out of memory in all three trials. At both 256 and 512 MiB, all three trials delivered the final source's clean Check Syntax monitor message, original handler response and actual GUI callback.

256 MiB was the smallest tested limit that completed this workload. Increasing to 512 MiB had no consistent timing advantage. Three trials per limit do not establish a universal sufficient limit or statistical significance. Full memory experiment and all nine observations.

What the experiment changed

Each trial used a fresh GUI process and isolated preferences on the same macOS 15 ARM64 runner, with cyclic 128/256/512, 256/512/128 and 512/128/256 ordering. Only the stock registered child-memory preference varied. The actual worker cap, final source, settings and tool registry were checked. The stock editor, lexer, tools and 20 ms coloring budget were retained; no appearance or autosave candidate was installed.

The setting is shared by Run and background analysis. It limits custodian-owned live memory, not total application RSS. At 256 MiB, observed whole-process peak RSS was 1.487–1.543 GB. It would be misleading to describe this as a 256 MiB application.

Completion remains slow

At 256 MiB, the actual final tool callback arrived 33.222–39.155 seconds after open. Observing both valid coloring and that callback took 33.274–44.117 seconds. The synchronous file-open command still blocked for 1.668–2.596 seconds, with further substantial event-loop delays. A lower time for the aborted 128 MiB arm is an early failure, not an equal-work speed comparison.

This is a capacity change, not a code optimization or a claim of faster editing. Large-file responsiveness and full DrRacket compatibility remain open. The separate autosave result below retains its original measured scope.

The installed host's save/recovery regression passed with the autosave guard on and off in separate fresh stock-128 test profiles. Those checks do not retime autosave at the new default or establish large-file performance of the combined build. The launcher observer verifies the registered preference in the actual GUI; worker-cap evidence comes from the separate workload experiment.

That installer milestone preceded the destination-built app checks above. Full official Racket 9.3 is still required, and Windows is untested. Installation, explicit choices and restore instructions.

Measuring the actual autosave call

2026-10-11

The retained DrRacket experiment reduced a specific source of synchronous autosave work: two redundant format-classification traversals. The required autosave classification, serialization, file writing, save hooks, recovery table and previous-artifact cleanup remain in the call. The original DrRacket editor and evaluator remain in use.

Method

Run 38061486888 used full official Racket 9.3 CS on a standard macOS 15 ARM64 runner, comparing pristine stock with an independently copied candidate runtime. Three fresh pairs alternated stock/candidate, candidate/stock, stock/candidate. Both arms used the same settings and a mixed-ASCII 1 MiB source fixture.

The genuine definitions editor loaded the file, made a one-character comment edit and reached lexer validity. Both arms were explicitly marked modified immediately before timing the real autosave method. Each Mac trial began with an existing recovery artifact and matching recovery-table entry, so all three pairs compared replacement saves. Exact recovery, original source bytes, settings and activation were checked.

The appearance changes, separate scan shortcut and experimental color budget were absent. This is the isolated autosave experiment, not a timing of the combined installation.

Mac results

  • Actual command medians: 266.735 ms stock → 172.400 ms candidate, 35.4% lower between arm medians.
  • Pair 1: 228.559 → 172.400 ms, 24.6% lower.
  • Pair 2: 284.354 → 162.689 ms, 42.8% lower.
  • Pair 3: 266.735 → 215.792 ms, 19.1% lower.
  • Queued GUI callback delay medians: 268.036 → 173.187 ms.

The median paired reduction is 24.6%; it is a different statistic from the 35.4% reduction between arm medians. These are descriptive results from three pairs, without a claim of statistical significance. All six Mac trials passed the exact source, recovery, settings, activation and lexer-validity gates.

Linux’s two matched first-save pairs improved by 24.7% and 32.6%. The other Linux pair had different prior recovery state and is excluded from that matched comparison. Mac and Linux results are not a cross-platform speed comparison.

Remaining limits

The candidate autosave call still blocked the GUI for about 163–216 ms. The queued callback includes the dirty precondition and small measurement snapshots; it is not physical input-to-photon latency. Whole-process peak memory was essentially unchanged. The experiment does not establish reduced retained memory, faster expansion, or elimination of major garbage-collection pauses.

Initial Mac lexer waits remained 34.373–39.619 seconds. Large-file readiness remains a larger unresolved problem. The original 20 ms lexer budget is retained; the 8 ms experiment was rejected and the separate scan shortcut is not enabled.

Custom extensions that count or throw from virtual traversal callbacks can observe fewer calls. This boundary is documented and is not a claim of arbitrary plugin parity. Verification-enabled conversion dialogs and crash/restart recovery UI remain outside this completed save proof.

The overall run failed in independent expansion-replay preparation, so that replay was not verified by that run. Combined performance has not been retimed.

Those checks covered the source installer requiring full official Racket 9.3. Later destination-built app acceptance is described above. Windows remains untested and full DrRacket equivalence is not established.
