# Run 38125605788: cold-empty toolbar diagnosis and narrow observer repair

## Finding

The failed assertion assumes an enabled `#lang` document, but the app was
intentionally launched empty into stock DrRacket's “No language chosen” state.
Stock 9.3 explicitly sets all three language-tool capabilities false in this
state and removes the corresponding buttons from panel children. This is a
source-proven observer precondition error, not evidence of native app tool loss.
It does not establish that the app's tools will work once a file is opened:
those live stages were withheld and still need execution.

No local Racket runtime or GUI was downloaded or executed. No remote mutation,
publication, additional app launch, or changes to product/builder inputs occurred.
The separate repair copy was authorized after the read-only diagnosis.

## Launcher / environment / metadata assessment

The frozen generator uses official `make-gracket-launcher` with the native variant
and no embedded replacement application. `runtime-dispatch.sh` matches exactly
`-A ADDON -R COMPILED_ROOTS -l drracket --`, then executes the generated native
image with the same arguments and resets `RACKET` to the configured official
runtime for child work. The source launcher supplies those same arguments to
console Racket in the source route. The shell bootstrap preserves the process
with `exec`, clears startup overrides, and runs the unchanged source launcher.

The frozen builder files are byte-identical to publication-34's used copies.
Preflight reports resolution of the correct modules, but explicitly does not
instantiate GUI modules, so it alone cannot establish successful tool loading.
The actual app did run the separately registered observer in the private profile,
and its original source hashes and private-first compilation/profile checks had
already passed before the frame assertion. The real dark window and the source
rule above explain the observed omission without modifying launcher flags,
collection links, package metadata, or source imports.

There is no affirmative evidence here of broken native argv, package discovery,
or collection configuration. No speculative launcher or packaging fix is staged.
The new observer records tool-capability registration to make a genuine missing
registration a distinct hard failure on the next run.

## Staged repair

`tool.rkt` now records the active document's real selected language position,
public module-language interface identity, filename/empty state, all three
capability registrations, and their values. It uses those facts before checking
the original localized order. Failure and success JSON retain that evidence.

The pure `expected-toolbar-labels` contract allows a two-button expectation only
when:
- the sequence is coldempty;
- the document is unnamed and contains zero characters;
- its real localized language position is the initial “No language chosen”;
- it is not module-language;
- all three tool capabilities are registered and all three values are false.

The initial coldempty stage explicitly requires this state. At warmfile/duplicate,
the original blank may remain and retain this state. Every other accepted frame
must be actual module-language and requires all five buttons. The observed labels
are filtered against all five names even in the two-button branch, so unexpectedly
visible language tools cannot be hidden by a narrower filter. Orientation,
Run/Stop object identity, genuine editor/canvas/frame identity, memory, theme,
native appearance, autosave, file contents and warm-document identity checks
remain intact. Every file stage additionally requires a current expected named
fixture with the exact same frame ID as a frame report that verified actual
module-language identity and all five toolbar controls. Inactive fixture tabs,
current blank tabs, unrelated files, unmatched frame IDs, and frames without
that proof cannot witness a pass. The observer neither opens a fixture nor
changes its language.
